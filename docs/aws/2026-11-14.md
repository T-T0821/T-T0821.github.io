## 📰 ニュース

### 1. AWS Secrets Managerがクロスアカウントレプリケーションに対応 {#news-1}

AWS What's New ・ 2026-11-13 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/secrets-manager-cross-account/)

プライマリのシークレットの同期コピーを別のAWSアカウントに保持できるようになりました。既存のマルチリージョンレプリケーションをアカウント境界を越えて拡張するもので、アクセス、バックアップ、災害復旧に使えます。中央のチームがシークレットを管理・ローテーションし、各利用アカウントは常に最新のローカルコピーを持てます。

::: tip 💡 影響・使いどころ
マルチアカウント環境でシークレットを集中管理しつつ、各アカウントで共有KMSキーなしに利用する構成を取りやすくなります。
:::

### 2. Security Hub CSPMがOrganizationsの宣言型ポリシーによる集中設定に対応 {#news-2}

AWS What's New ・ 2026-11-13 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-cspm-org-policies/)

宣言型ポリシーで、組織内の全アカウント・全リージョンにSecurity Hub CSPMを有効化し、有効にするセキュリティ標準やコントロールを定義できます。全体にも、特定のアカウントとリージョンの組み合わせにも適用でき、各アカウントの設定をポリシーに沿わせて構成のドリフトを抑えます。

::: tip 💡 影響・使いどころ
組織全体でのCSPM展開と設定統制をポリシーで一元化でき、アカウントごとの個別設定の運用負荷を減らせます。
:::

### 3. Aurora/RDSでGraviton5ベースのR9gインスタンスが利用可能に {#news-3}

AWS What's New ・ 2026-11-12 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-aurora-rds-postgresql-mysql-mariadb-r9g-instances/)

Aurora（PostgreSQL互換・MySQL互換）とRDS for PostgreSQL、MySQL、MariaDBでGraviton5ベースのR9gインスタンスが一般提供されました。Graviton4ベースの同等サイズと比べ、最大30%の性能向上、オンデマンド料金での最大22%の価格性能比向上とされています（エンジン、バージョン、ワークロードによる）。

::: tip 💡 影響・使いどころ
既存のDBインスタンスの移行候補になるため、自社ワークロードで性能とコストを検証する価値があります。
:::

### 4. Amazon CognitoがOAuth 2.0トークン交換（RFC 8693）に対応 {#news-4}

AWS What's New ・ 2026-11-12 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/)

ユーザーの代理で動作するサービスやAIエージェントが、ユーザーのトークンを特定の下流サービス向けにスコープされた新しいトークンへ交換できるようになりました。従来は元のトークンを転送するか、独自にトークン発行の仕組みを作る必要がありました。

::: tip 💡 影響・使いどころ
マイクロサービスやAIエージェントの呼び出しチェーンで、最小権限のトークンを標準仕様に沿って受け渡せます。
:::

### 5. Bedrock AgentCore IdentityがOAuth 2.0ディスカバリーURLに対応 {#news-5}

AWS What's New ・ 2026-11-13 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/bedrock-agentcore-oauth2-discovery/)

### 6. Aurora PostgreSQLのexpress configurationがCloudFormationに対応 {#news-6}

AWS What's New ・ 2026-11-13 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-postgresql-cloudformation/)

## 📄 論文

### 1. 起動処理の共有と事前ウォームアップによるサーバーレスLLMの高速コールドスタート {#paper-1}

arXiv ・ Hongjin Kim, Igjae Kim, Kwanghoon Choi, Minho Ha ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.16180)

<small>原題: Fast Serverless LLM Cold Starts by Sharing and Prewarming Startup Work</small>

サーバーレスLLM基盤のコールドスタートは約1分かかり、重みのロードは全体の5〜11%にすぎません。残りはコンパイル、メモリプロファイリング、ランタイム初期化で、サーバーごとに同じ処理が繰り返されています。提案手法Cairnは、最初にモデルを起動したサーバーが重みとエンジンの成果物をクラスター共有のCXLメモリプールに公開し、他のサーバーが再利用する仕組みです。

::: tip 🔍 注目ポイント
LLM推論のコールドスタートで重みロード以外が支配的という指摘は、サーバーレス推論基盤の設計を考えるうえで参考になります。
:::

::: info 📝 落合フォーマット

**どんなもの？**

サーバーレスLLM基盤で、モデルワーカーのコールドスタート（約57〜85秒）のうち重みロードは5〜11%に過ぎず、残りのコンパイル・メモリプロファイル・ランタイム初期化が各サーバーで重複実行されている点に着目した研究。Cairnは、サーバー間で共有できる処理と、モデルに依存せず事前実行できる処理を取り除くことでコールドスタートを短縮する。重みやエンジン成果物をクラスタ共有のCXLメモリプールに置き、モデル非依存の準備はウォームコンテナで済ませる。

**先行研究と比べてどこがすごい？**

先行研究の多くは重みの高速ロードや、予測したモデルの事前配置（サーバー単位）に注力していた。本研究はコールドスタートの処理を「共有可能／事前準備可能／プロセス固有」に分類し、コンパイルキャッシュ・モデル情報・コンパイラキー・CUDAグラフのメモリ推定といったモデル固有成果物をクラスタ全体で再利用する点が新しい。また、使用済みコンテナの補充をzygote（テンプレートプロセス）からのforkで行い、予測なしで全GPUにウォームコンテナを維持できる。

**技術や手法のキモはどこ？**

最初にモデルを起動したサーバーが重み・メタデータ・コンパイルキャッシュ・コンパイラキー・CUDAグラフメモリ推定を、モデルと互換性フィンガープリントをキーとする不変エントリとしてCXLプールに書き込み、小さなコーディネータが索引と空き領域を管理する。書き手は単一（SWMR）、フラッシュ後に有効化、読み手はキャッシュ無効化してから読むことでハードウェアコヒーレンスなしで運用する。他サーバーはGPUがプールから重みを直接DMAコピーし（初期化と重なる非同期ロード）、他の成果物はエンジンに復元または注入する。モデル非依存部分（import、CUDA初期化、エンジンコア起動）は待機するウォームコンテナで済ませ、CUDA初期化後はforkできないため、CUDA未初期化のzygoteから置換用コンテナをforkして補充する。

**どうやって有効だと検証した？**

ServerlessLLMをvLLM v0.20に移植したsllm+vLLM上で、1B〜14Bの6モデル、2台のサーバー（NUMAリモートメモリによるCXLプールのエミュレーション）で評価した。チェックポイントを持たないサーバーでのコールドスタートが57〜85秒から11.0〜21.0秒へ4.1〜5.2倍高速化し、Azure Functionsトレースに従う1時間のリクエスト列では中央値TTFTが32.5秒から11.8秒へ64%低下した。16サーバーのシミュレーションでは3.2 req/sでタイムアウトが15.6%から2.1%に減った。アブレーションではコンパイルキャッシュの寄与が最大で、除くと2.6倍遅くなった。

**議論はある？**

CXLスイッチがなく、NUMAリモートメモリ＋VM共有NVDIMMによるエミュレーションで、実機CXLでの挙動は未検証である。ベースラインが各サーバーのNVMeにチェックポイントを持つため、重みプール化・非同期ロード単体の時間短縮は小さく、主な利点はメモリ・ストレージ節約となる。CUDAグラフはプロセス固有のため従来通りキャプチャが必要で（Medusaとは直交）、プールへの初回書き込みでは初回ロードが22〜23%延びる。また、アイドルのウォームコンテナがホストメモリ約2.9GBなどを常時消費する。

**次に読むべき論文は？**

- ServerlessLLM: Low-Latency Serverless Inference for Large Language Models：Cairnの実装ベースであり、チェックポイントのマルチ階層ストアと高速ローダという比較対象の基本設計を理解できる。
- Medusa: Accelerating Serverless LLM Inference with Materialization：Cairnがプロセス固有として残したCUDAグラフのキャプチャを事前マテリアライズで省く手法で、Cairnと直交し組み合わせ可能である。
- SOCK: Rapid Task Provisioning with Serverless-Optimized Containers：Cairnのzygoteによるfork補充の元となるテンプレートプロセスの手法と、ウォームプールの設計を学べる。

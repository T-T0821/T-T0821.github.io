### 1. 次世代 AgentCore ランタイムが新規ランタイムの既定に {#news-1}

AWS What's New ・ 2026-11-12 ・ [原文を読む ↗](https://aws.amazon.com/about-aws/whats-new/2026/11/new-agentcore-runtime-default/)

Amazon Bedrock AgentCore の新規ランタイムは、次世代ランタイムが既定になりました。初期化済みエージェントのスナップショットからセッションを復元し、処理量に応じてコンピュートとメモリを拡張、アイドル時はゼロまでスケールします。各セッションは引き続きハードウェア分離された Firecracker microVM で動作します。

::: tip 💡 影響・使いどころ

### 2. AWS Nitro Sandboxes が EKS・ECS・EC2 で利用可能に {#news-2}

::: tip 💡 影響・使いどころ

## 📄 論文

### 1. SBC クラスター上のエネルギー比例型サーバーレスコンピューティング {#paper-1}

arXiv ・ Yuliya Sasinskaya, Natalie Carl, Niklas Kowallik, David Bermbach ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.14026)

<small>原題: Energy-Proportional Serverless Computing on SBC Clusters</small>

サーバーレス関数がステートレスであることを利用し、スケールトゥゼロを関数インスタンスから物理ノードまで拡張して、エネルギー比例性を実現する方式を示しています。tinyFaaS を基に構築したプラットフォームは、ノードの電源状態をワーカー選択の一部として扱います。

::: tip 🔍 注目ポイント
アイドル時の消費電力というサーバーレスの見落とされがちな課題に取り組んでいます。
:::

::: info 📝 落合フォーマット

**どんなもの？**

サーバーレス関数がステートレスである性質を利用し、scale-to-zero を関数インスタンスから物理ノードにまで拡張して、サーバーレスクラスタの消費電力を負荷に比例させる研究。tinyFaaS を拡張し、シングルボードコンピュータ（SBC）クラスタ上でワーカーノードを遊休時に電源OFF、負荷時に電源ONするプラットフォームを実装・評価した。

**先行研究と比べてどこがすごい？**

ノード単位の電源遮断自体は Muse や NapSAC など既存手法にもあるが、本研究はサーバーレスでは全関数がステートレスであり、ワーカー選択と電源制御を同一プラットフォームが担える点に着目した。ワーカー選択の判断に電源状態を組み込み、状態移行なしでノードを落とせる構成を示した。既存のコンポーネント内電力管理（DVFS等）やインスタンス単位のキープアライブ制御と相補的な位置づけである。

**技術や手法のキモはどこ？**

リーダーノードが全呼び出しを受けてロードバランスとワーカーの電源制御を行い（リーダー自身は常時ON・実行はしない）、ワーカーは sleeping／waking／active の3状態を遷移する。呼び出しごとに、まず処理中数が L 未満で最も負荷の低い active ワーカーを選び、なければ sleeping ワーカーを起こし、それも無ければ飽和ワーカーにフォールバックする。コントローラが、アイドル時間が閾値 τ を超えたワーカーを、状態移行なしでリレー経由により電源遮断する。最低稼働台数 H（powered headroom）も設定でき、実験では τ=60 s、L=10、H=0 を用いた。

**どうやって有効だと検証した？**

Raspberry Pi 4B 4台（リーダー1＋ワーカー3）で全ノードの電圧・電流を50Hzで実測し、同一クラスタを常時ONにした構成と比較した。Sobel エッジ検出を、sparse（2分に1回）、Azure Functions トレース再生の bursty、continuous（10 req/s）の3ワークロードで各4回実行した。平均電力は bursty で39.6%、sparse で46.7%削減され、continuous では差は-0.6%（95%CI [-2.4, +1.3]）だった。bursty の中央値レイテンシに検出可能な変化はなかったが、ワーカー起動に約53秒（48〜58秒）かかるため、バースト先頭の呼び出しで95パーセンタイルが51.9秒増えた。sparse では中央値が0.17秒から49.5秒に悪化した。

**議論はある？**

コストは電源OFF時に到着した呼び出しの約1分の起動待ちに集中する。リーダーによる代理実行、powered headroom（H≥1）、日週周期を使った予測起動で緩和できる可能性があるが、本論文では未評価である。リーダーとリレーの残余電力は削減できず、continuous 負荷では least-loaded 選択のため節電効果がほぼ無かった。また、評価は1関数・小規模クラスタに限られ、SDカード故障の事例や、モデル重みを失う AI アクセラレータ向けの適用可否など、課題が残る。

**次に読むべき論文は？**

- Serverless in the Wild: Characterizing and Optimizing the Serverless Workload at a Large Cloud Provider：評価で使われた Azure Functions トレースの出典で、サーバーレス負荷の特性とキープアライブ予測を理解できる。
- PowerNap: Eliminating Server Idle Power：ノード全体を落とす本手法とは対照的に、ミリ秒単位でサーバーを低電力状態へ遷移させる別アプローチで、比較の視点が得られる。
- Towards Energy-Efficient Serverless Computing with Hardware Isolation：起動から終了まで呼び出しごとに専用SoCを使う、本研究と同グループによるより極端なハードウェア電源制御の提案である。

:::

### 2. WebAssembly コンポーネントからの AWS サーバーレスインフラ構築 {#paper-2}

arXiv ・ Philipp Vollmer ・ [論文を読む ↗](https://arxiv.org/abs/2611.11293)

<small>原題: AWS Serverless Infrastructure from WebAssembly Components</small>

WebAssembly コンポーネントのインターフェース定義言語である WIT から、クラウドインフラをプロビジョニングする Infrastructure from Code の手法を提案しています。アプリケーションのコードとインフラ定義が緩く結びついていることで、参照先が存在しない、権限が同期しないといった誤りが生じる問題に対処します。

::: tip 🔍 注目ポイント
コードとインフラ定義のずれという実務上の問題に、型付きインターフェースから取り組む点が注目されます。
:::

::: info 📝 落合フォーマット

**どんなもの？**

AWS Lambda が S3 バケットにアクセスするサーバーレスアプリを対象に、WebAssembly コンポーネントのインターフェース記述言語 WIT を唯一の情報源として、インフラ定義（CDK）と最小権限の IAM 権限を自動導出する Infrastructure from Code の手法を提案した。あわせて、コンポーネントを Lambda 上で動かし S3 へのアクセスを capability として与える汎用ランタイムも構築した。これにより、バケットの不在や権限不整合といったデプロイ時エラーの防止を目指している。

**先行研究と比べてどこがすごい？**

既存ツール（Cloudflare Workers、Winglang、Ampt、Encore、wasmCloud、Spin、Pulumi）との比較表では、言語非依存・単一の情報源・権限の自動生成・capability ベースのセキュリティの4点を併せ持つのは本手法のみとされる（ただし機能範囲は Lambda と S3 に限定され、はるかに小さい）。「1つの言語（WIT）に対し2つの整合したインタプリタ」というパラダイムを採用している点が特徴である。

**技術や手法のキモはどこ？**

第1のインタプリタ（extractor）は WIT を読み、aws:s3/blob と aws:lambda/handler の特殊インターフェースを探して、外部 ID（@external-id）から S3 バケットの CDK 構成と Lambda、実行ロールへの必要な IAM 権限を生成する。第2のインタプリタはランタイム（runtime クレート）で、動的リンカとして import された capability を探し、外部 ID が指すバケットへ put-file する関数を組み立ててコンポーネントにリンクする。コンポーネントは既定で I/O 能力を持たないサンドボックスで動くため、環境変数や TCP によるアクセスの偽造はできない。整合性の性質として、各 import に対しバケットが作られ、その関数が呼ぶ AWS アクションに対応する IAM 文だけが生成されることを定式化している。

**どうやって有効だと検証した？**

ベースライン（CDK と handler を別管理する構成）と比較し、バケット名の誤設定と権限の誤設定は構成上不可能か、ローカルテストで検出できることを示した。ベースラインでは同様の例（EnvMismatch、MissingGrant）が実行時にクラウド上で初めて失敗する。アクセス偽造もランタイムのテストで失敗し、ベースラインでは検出されずに成功した。1つ目の整合性性質はテストで裏付け、2つ目は S3 アクション記録のテストで「証拠」を示すにとどまる。性能面では、コールドスタートの p50 は native 5.3 ms、wasm 105.6 ms、事前コンパイル版 12.5 ms（約8倍改善）で、デプロイ zip は native 1.64 MB に対し wasm 約15.2 MB、sort_unstable は native が wasm より約1.5〜2.2倍高速だった。

**議論はある？**

WIT の不安定機能 external-id に依存しており、バケット名を設定できないためステージ別デプロイが難しい（CDK 生成名の注入やテンプレート化が解決案として挙げられている）。対象エラーの発生頻度に関する実証データはなく、ランタイム自体がセキュリティ境界となる点にも注意が必要である。今後は、WIT に依存関係の設定を表す言語要素を加え、より多様なインフラ部品や相互作用へ拡張することが課題とされている。

### 3. AWS Trainium 向けカスタム GPSIMD オペレーターによる LLM メモリの高速化 {#paper-3}

arXiv ・ Zifan He, Jason Cong ・ [論文を読む ↗](https://arxiv.org/abs/2611.11820)

<small>原題: Exploiting Native Hardware Heterogeneity: Custom GPSIMD Operators for Accelerating Emerging LLM Memory on AWS Trainium</small>

DeepSeek-V4.1-Flash の Engram のような新しい LLM メモリモジュールは、不規則な整数処理と密な計算が混在します。Trainium の NeuronCore が持つ密なエンジンとカスタマイズ可能な GPSIMD エンジンの組み合わせを活かす手法を扱っています。

::: tip 🔍 注目ポイント
Trainium 上で新しい LLM 構成要素を実装する際の、ハードウェア特性の活用例として参考になります。
:::

::: info 📝 落合フォーマット

**どんなもの？**

DeepSeek-V4.1-Flash の Engram のように、不規則な整数処理（64bit n-gram ハッシュ、疎なテーブル参照）と密な計算（GEMM、ゲート）が混在する LLM メモリモジュールを、AWS Trainium 3 の NeuronCore 内蔵のヘテロ構成（GPSIMD Engine と密演算エンジン）で高速化した研究です。公式には Trainium 2/3 の NKI カーネルから GPSIMD のカスタム演算子を使えないため、C++ のカスタム演算子をコンパイルし、NKI カーネルをコンパイルして得た NEFF に注入するツールチェーンを構築しました。

**先行研究と比べてどこがすごい？**

公式のカスタム C++ 演算子ツールチェーンは NeuronCore-v2 のみ対応で、Trainium 3 では拒否され（NCC_EVRF030）、PyTorch/XLA 経由でしか呼べず、Neuron 2.33 以降はメンテナンスモードです。本研究は Neuron ランタイムの GPSIMD コード読み込み・実行の仕組みを解析し、NKI カーネルから GPSIMD 演算子を呼べる経路を現行のソフトウェアスタックのまま実現した点が新しいです。また、GPU-FPGA での役割分担と同じ考え方を、Trainium のチップ内ヘテロ性に適用しています。

**技術や手法のキモはどこ？**

NKI 側で gp.call(...) が marker 命令（タグ付きの TENSOR_SCALAR_ARITH_OP と MEMSET）を出力し、通常どおりコンパイルします。その後 gpsimd-neff が NEFF の Pool0.bin から各タイルの SBUF 位置を読み取り、C++ 演算子を GPSIMD コア用にビルドして ops.so を NEFF に追加し、marker を 1 つの KERNEL_CALL 命令に置換します。このとき、セマフォ S[3] の待ち回数が全体のスケジュールを表すため、置換で消える marker 分（例では 9）を加算し、後続の wait を整合させる必要があります。Engram では、Horner 法で 32bit に分割していたハッシュを 8 コアの 64bit 演算（Barrett 縮約）で直接計算する ngram_hash と、シャードに当たる行のみの gather リストを作り DMA 数を減らす engram_hits の 2 演算子を実装しました。

**どうやって有効だと検証した？**

trn3.48xlarge の 1 NeuronCore で、vLLM Neuron の手最適化 NKI ベースラインと比較しました（重みは実値ではなくランダム値で、行 ID はモデルのハッシュ分布に従う設定）。n-gram ハッシュは decode で 86.95µs から 48.45µs（1.79 倍）、テーブル取得は prefill T=1024 で 506.9µs から 102.4µs（4.95 倍、indirect DMA は 192 から 6 に減少）になりました。Engram 全体では decode で 1.05 倍、prefill（1024/2048 トークン）で 1.14 倍で、この 2 処理が Engram 時間の約 1/5（prefill）〜1/7（decode）を占めるため、理論上限は約 1.27 倍（prefill）、1.17 倍（decode）と述べています。さらに NKI Library 比で argsort が 6.6〜40 倍、BM25 スコアリングが 15〜27 倍、重複インデックスの scatter-add が 4.45 倍の高速化を示しています。

**議論はある？**

現状のツールチェーンは、Trainium 3 に対応する Xtensa 構成がないためベクトル命令を使えず（生成コードがコアをハングさせる）、浮動小数点もソフトウェア実行（float32 加算 117 サイクル）で、タイルアドレスはビルド時固定（カーネル再コンパイルのたびに再ビルドが必要、コード 64KB 等の制約あり）です。著者らは公式サポートでの解決を期待しており、また本ツールチェーンは AWS 内部実装を反映するとは限らず参考情報として扱うよう注記しています。Engram 全体の効果は最大 1.14 倍にとどまり、将来の Engram 層の増加で寄与が増えると見込まれます。

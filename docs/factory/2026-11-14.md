### 1. 群れを刺す：ツインコントローラ型OTハニーポットから攻撃者の情報を抽出する {#paper-1}

arXiv ・ Canyon Grey Dell'Omo, Joao Pedro de Carvalho Voltani ・ [論文を読む ↗](https://arxiv.org/abs/2611.13406)

<small>原題: Stinging the Swarm: Extracting Attacker Intelligence from a Twin-Controller OT Honeypot</small>

言語モデルエージェントがフィールドバス経由で産業用コントローラを操作し、高速かつ協調的に攻撃する状況を想定している。提案するTalosは、各リクエストをミリ秒で判定するインラインゲートで、敵対的と判断したエージェントを実機に忠実な模擬プラントへ誘導し、攻撃を無害化しつつ情報を取得する。検出から隔離、ミラー、抽出までの一連の流れを評価したとされる。

::: tip 🔍 注目ポイント
産業用コントローラのセキュリティ対策と、実機を模したデジタルツイン的な構成の応用例として実務上の関心が高い。
:::

::: info 📝 落合フォーマット

**どんなもの？**

LLM エージェントが Modbus 等のフィールドバス経由で産業用コントローラを攻撃する状況を想定し、インラインのゲート「Talos」を提案した研究。ゲートは全リクエストをミリ秒で判定し、敵対的と判断したエージェントを実機の鏡像ツイン（デコイ）へ静かに振り分ける。実機を守りつつ、デコイ上で攻撃を継続させて攻撃者の情報を抽出する。

**先行研究と比べてどこがすごい？**

従来の ICS/LLM ハニーポットは「本物らしく見せて攻撃者を引き留める」ことが主目的だったが、本研究は実機保護を保証するインラインゲートの後段にミラーを置き、エージェント型攻撃者からの情報抽出を能動的に行い、その収量で評価する。また、発話に対する秘匿指示は device I/O の形をとった要求（診断フォームやレジスタ書き込み）では働かないという、運用層での情報抽出の仕組みを示した点が新しい。

**技術や手法のキモはどこ？**

ゲートは小型オンデバイスモデルと決定論的な高速パスで各リクエストを allow/cache/defer/deny に分類し、エージェント ID ごとに評判と隔離状態を管理する。設定値・パラメータレジスタと未マップレジスタへの書き込みは拒否するが、非常停止などの安全側の操作は許可する。敵対的と判定されたエージェントは同じデバイスファミリー・シードで作った許容的なミラーツインへ誘導され、そこでペルソナ質問・セッション登録・診断レポートフォームといったルアーが書き込み継続中に発火する。ツイン上の書き込み・レジスタトラフィックとフォーム内の software_client や registers_modified といった不随意の手がかりを集約し、攻撃者プロファイルを構築する。

**どうやって有効だと検証した？**

秘匿の度合いが異なる4段階（なし／非開示ルール／「ハニーポットだ」という警告／偽装身分）×各600、計2,400の攻撃エージェント（単一の無検閲 Llama-3.3-70B 派生モデル）で検証した。実機に着弾した書き込みは全段階でゼロで、損傷経路への書き込みは99.4〜100%がゲートで阻止され、未マップレジスタは例外なく拒否された。ゲートが通した1,427件の書き込みもデバイス側の範囲検証がすべて拒否した。判定の32〜40%はモデル駆動で推論タイムアウトはなかった。情報抽出では、非開示ルール群の55%がミラーへ昇格し38%（231体）がミラー＋ルアーで読み取られ、talkative な群は隔離前に自発的に開示した（bare 100%、cover-story 96%）。1,621件の診断提出から9種のクライアント文字列と86種の標的レジスタ集合が得られ、偵察先行、0xFFFF の書き込み（21,098件中19,330件）、制御レジスタ0・1狙い、pymodbus 3.5 という攻撃者像を事前知識なしで再構成できた。

**議論はある？**

攻撃者モデルが単一の無検閲モデルであること、合成の水ポンプ用ドライブファミリー1種・固定シードのみであること、身元情報は自作の作り話で帰属には使えないことが限界で、モデル間やデバイス間の一般化、デコイを見破られる可能性は未検証である。パラノイド群（撤退して沈黙する層）は抽出できず、ルアーは書き込み継続中のみ発火するため抽出量は保守的な見積もりとなる。群の蓄積曲線も1通りの順序に基づくため、ブートストラップによる信頼区間が必要とされている。

**次に読むべき論文は？**

- Network- and Device-Level Cyber Deception for Contested Environments Using Reinforcement Learning and Large Language Models：LLM と検証層で物理制約を守るデバイスレベルのデコイ設計を扱っており、本研究のミラーツインの忠実度を考える上で比較対象になる。
- A Hybrid Honeypot for Cyber Detection and Deception in Industrial Control Systems：従来の ICS ハニーポットの構成と評価を把握でき、Talos の位置づけを確認できる。
- LLM in the Shell: Generative Honeypots：LLM による生成型ハニーポットが実際の攻撃者をどう引き留めるかを示した代表的な先行研究で、本研究の「引き留める」から「抽出する」への違いが理解しやすくなる。

:::

### 2. IoTPwnBench：IoTファームウェアのセキュリティ解析用合成ベンチマーク {#paper-2}

arXiv ・ Luca Ferrari, Marco Alecci, Luca Verderame, Jacques Klein ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.15316)

<small>原題: IoTPwnBench: A Synthetic Benchmark for IoT Firmware Security Analysis</small>

IoTファームウェアのセキュリティツールの開発・評価には、弱点が事前に分かっていて実機上で再現できる対象が必要だと指摘している。実製品のファームウェアは、ハードウェア依存や未文書化の欠陥のために、ツールが何を検出すべきか定めにくいという課題がある。これに対し合成ベンチマークを提示している。

::: tip 🔍 注目ポイント
組み込み機器や装置のファームウェア脆弱性検査ツールを評価する際の基準づくりに参考になる。
:::

::: info 📝 落合フォーマット

**どんなもの？**

IoT機器ファームウェアのセキュリティ解析ツールを評価するための合成ベンチマークIoTPwnBenchを提案した研究。11種のデバイスプロファイル×86の弱点シナリオ（28のCWEクラス）から716個の脆弱ファームウェアイメージを構築し、各々に弱点のみを除いた修正版ツイン716個を対応付けている。センサ・アクチュエータをシミュレートした稼働中のデバイスアプリを備え、QEMUで起動できる。

**先行研究と比べてどこがすごい？**

B4IoTなどの既存ベンチマークは複数の弱点が混在するコンテナイメージや実ファームウェアの集合で、何を検出すべきかの根拠が曖昧だった。本研究は1イメージ1つの対象弱点（主CWE）に絞り、文書化されたペイロードと観測可能なシグナルをツール判定と独立したground truthとして与える。さらに修正版ツインとの対比で誤検知を測れ、デバイスプロファイルと弱点モジュールを分離して再利用できる点が新しい。

**技術や手法のキモはどこ？**

Yocto Project（6.0.3）で、デバイスプロファイル（管理アプリ、周辺機器仕様、HTTP/MQTT/Modbus等のネイティブサービス）と弱点モジュールを1つずつ選ぶ短いイメージレシピからカーネルとext4ファイルシステムを生成する。共通シミュレータが平均回帰過程、季節項＋ノイズ、マルコフ過程、単調増加カウンタなどでセンサ値を更新する。修正版モジュールは弱点を含むファイルだけを置き換え、ツインのレシピはスクリプトで自動生成する。ビルドはリビジョン固定のDockerコンテナ内で行い、ビット単位で再現可能であることを確認している。

**どうやって有効だと検証した？**

全イメージをQEMUで起動し、文書化したペイロードを手動で実行して観測シグナルが記載と一致するか確認し、差異があればモジュールを修正して再確認した。ビルドの再現性はビット同一性で検証し、一部のカタログにはスクリプト化した回帰テストがある。一方、既存の解析ツールを実際に評価する実験は未実施で、本文では設計が支える利用例の提示にとどまる。

**議論はある？**

弱点は設計されたものであり実環境での頻度や形態を反映しない。86シナリオは56モジュールの派生で独立した弱点数は画像数より少なく、単一弱点ゆえに弱点間の相互作用や非対象の欠陥は扱えない。また対象はLinux系・QEMU・シミュレート周辺機器に限られ、MCU/RTOSや実機は対象外で、検証は手動中心である。今後はEMBAやFACT_core、IoTFuzzer等の評価、デバイスクラスの追加、reached/triggered/detectedを分けたスコアリングを予定している。

**次に読むべき論文は？**

- Linux-based IoT benchmark generator for firmware security analysis tools (B4IoT)：弱点選定の元となり、本研究が直接の比較対象とする最も近い先行ベンチマークであるため。
- Magma: a ground-truth fuzzing benchmark：到達・トリガー・検出を分けて評価するground truthベンチマークの設計で、本研究の将来のスコアリング拡張の手本となるため。
- IoTFuzzBench: a pragmatic benchmarking framework for evaluating iot black-box protocol fuzzers：実ファームウェアに基づくIoTベンチマークとの違いを理解し、動的テスト評価の文脈を把握できるため。

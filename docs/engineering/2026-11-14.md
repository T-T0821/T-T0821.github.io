### 1. FOSSプロジェクトでメンテナが指摘した「AIスロップ」PRの実証研究 {#paper-1}

arXiv ・ Hugo Raskin, Xavier Devroey, Benoît Vanderose ・ [論文を読む ↗](https://arxiv.org/abs/2611.15159)

<small>原題: An Empirical Study of Maintainer-Identified AI Slop Pull Requests in Free and Open Source Software Projects</small>

生成AIによって貢献の障壁が下がり、低品質・低価値なAI生成PRが現れていることを背景に、メンテナが特定したAIスロップPRの発生状況をプロジェクト単位で調べた研究である。従来のプラットフォーム全体や理論、実務者の証言による研究とは異なる視点を取る。

::: tip 🔍 注目ポイント
OSSの運営やレビュー負荷に直結する問題を、プロジェクト単位のデータから検証している。
:::

::: info 📝 落合フォーマット

**どんなもの？**

GitHubの人気・成熟OSSリポジトリ10,000件から、メンテナが「slop（AIスロップ）」と判断して題名やラベルで印を付けたPR 1,786件を収集し、その増加傾向・特徴・扱われ方・フラグ/クローズ理由を実証的に調べた研究。生成AIがOSSの外部貢献とメンテナの負担に与える影響を、プロジェクト単位で捉えようとしている。

**先行研究と比べてどこがすごい？**

従来のAIスロップ研究は理論的整理、プラットフォーム全体の分析、実務者の発言の分析が中心で、プロジェクト単位でメンテナ自身が識別したスロップPRを定量化した点が新しい。また、メンテナや bot が示した理由をオープンコーディングして、具体的な理由から「AIっぽい」という直感的・思想的な理由までを並べた分類体系（タクソノミー）を提示した。データセット、スクリプト、コードブックも成果物として挙げている。

**技術や手法のキモはどこ？**

タイトルに slop / ai junk / ai spam を含むPR、およびラベルに slop 等を含むPRを GitHub API で収集し、GraphQL でコミット数・コメント・変更行数・著者情報を取得した。第一著者が偽陽性173件を除去し（精度91.17%）、リンクされた issue の有無、AI利用の開示、著者の抗議、フラグ/クローズ者などを手作業で注釈した（Cohen's κ 0.90〜1.00）。理由については3名の著者が Saldaña の方針でオープンコーディングし、軸足コーディングでカテゴリ化した（解釈主義の立場から一致度は報告せず）。

**どうやって有効だと検証した？**

対象は10,000リポジトリ中76件で、スロップPRは2025年9月頃から増え、2026年5月に342件でピークとなった（その後も月300件超で推移）。PRの94.1%は削除より追加が多く、97.9%がマージされずにクローズされ、マージされたのは0.6%だった。クローズまでの時間の中央値は約0.27日である。AI利用を最初から開示したのは13.9%、メンテナの依頼後に開示したのは1.6%で、メンテナによるフラグは97.5%、bot によるクローズは5.9%だった。理由が示されなかったものが最多（439件）で、AIポリシー違反（141件）や「AIっぽく見える」（117件）が続いた。huggingface/transformers と pallets/click の2リポジトリで全体の約42%を占めるため、これらを除いた結果も併記している。

**議論はある？**

検出の再現率は推定できず、結果はスロップPRの発生率の下限値にとどまる。また、人気・成熟プロジェクトに限定され、GitHub上の用語にも依存するため、一般化には限界がある。メンテナの判断はAI生成物と単なる低品質な貢献を区別できておらず、理由は事後的な合理化の可能性がある。さらに、2リポジトリへの偏りや削除されたPRによる生存者バイアスもあり、傾向は因果ではなく相関として扱う必要がある。観測窓は2026年7月でピーク付近に終わっており、今後の増減は予測できない。

**次に読むべき論文は？**

- "AI Slop is DDoSing Open Source": Understanding the Impact of AI-Generated Contributions on Open Source Sustainability：OSSにおけるスロップPRの影響を、時系列分析と実務者への調査で検証した最も近い先行研究であり、本研究と比べて読むと位置づけが分かる。
- "An Endless Stream of AI Slop": How Developers Discuss the Burden of AI-Assisted Software Development：開発者がAIスロップをどう捉え対処しているかを質的に整理しており、本研究の理由分類と対応づけて読める。
- AI Policy, Disclosure, and Human in the Loop: How Are Contribution Guidelines Adapting to GenAI?：AIポリシー違反が最多級の理由として挙がっており、各プロジェクトの貢献ガイドラインがどう対応しているかを理解できる。

:::

### 2. AI支援開発における技術的負債のリスク：実務者の知見 {#paper-2}

arXiv ・ Nazia Jahan, Nafisa Alam, Sourov Debnath, Arafat Rahman ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.15310)

<small>原題: Technical Debt Risks in AI-Assisted Software Development: Insights from Practitioners</small>

バングラデシュのソフトウェア専門家137人へのアンケートと20人へのインタビューによる混合手法の研究。10の技術的負債の観点から、AI生成コードに対して認識されているリスク、保守への影響、検証の実践などを調べている。

::: tip 🔍 注目ポイント
AIコーディング支援の導入で懸念される技術的負債について、実務者の認識を実証的に示している。
:::

::: info 📝 落合フォーマット

**どんなもの？**

AI コーディングアシスタントが生成するコードや開発プラクティスに伴う技術的負債のリスクについて、ソフトウェア実務者の認識を明らかにする研究。バングラデシュのソフトウェア専門家を対象に、認識されるリスク、その発生状況、保守への影響、検証の実践などを調べている。

**先行研究と比べてどこがすごい？**

AI 支援開発における技術的負債の懸念を、既存の10個の技術的負債の次元に当てはめて実務者の視点から体系的に調べている点が特徴。アンケートとインタビューを順に行う混合研究法を用い、バングラデシュという特定の地域の実務者を対象にしている。

**技術や手法のキモはどこ？**

逐次的な混合研究法を採用している。まず137名のアンケート回答を集め、続いて20名の専門家に追加インタビューを行った。10の既存の技術的負債の次元を分析の枠組みとして、認識されるリスク、寄与する状況、保守上の影響、検証プラクティスなどを検討している。

**どうやって有効だと検証した？**

137名のアンケート回答と20名のフォローアップインタビューによる実務者データに基づく調査である。アブストラクトが途中で途切れており、具体的な数値結果や主要な発見は確認できない。

**議論はある？**

対象がバングラデシュの実務者に限られるため、他地域や他の開発環境への一般化には注意が必要と考えられる。また、結果は実務者の認識に基づくもので、実際のコード品質や負債の測定とは別である。本文が取得できていないため、詳細な限界や今後の展望は確認できていない。

<small>※ 本文を取得できなかったため、アブストラクトのみに基づいています。</small>

:::

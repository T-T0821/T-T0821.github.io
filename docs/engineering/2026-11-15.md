## 📄 論文

### 1. AI時代のコード行数か？エンジニアのトークン消費量は何を測っているのか {#paper-1}

arXiv ・ Shyam Agarwal, Olga Lvova, Agnia Sergeyuk, Anastasiia Serova ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.13396)

<small>原題: The AI Era's Lines of Code? A Case Study on What an Engineer's Token Spend Measures</small>

JetBrainsの404人のエンジニアについて、5週間のコーディングエージェントのトークン使用量とコミットを突き合わせ、社内調査も分析しています。トークン消費は主に個人間で差があり、消費の多い人は週をまたいでほぼ変わりませんでした。

::: tip 🔍 注目ポイント
AI導入の指標としてトークン消費を使う組織が増える中、その指標の意味を実データで検証している点が注目されます。
:::

::: info 📝 落合フォーマット

**どんなもの？**

エンジニアのトークン消費量（token spend）が、生産性や成果の指標として何を測っているのかを、JetBrainsの404人のエンジニアの5週間分のコーディングエージェント利用ログとコミット、および412人の社内サーベイを結び付けて調べた事例研究である。トークン消費は成果ではなく「エージェントをどれだけ多様な業務に使ったか」を測るものだと結論づけ、資源会計に限った利用と、タスクと成果の証拠に基づく評価を推奨している。

**先行研究と比べてどこがすごい？**

従来の研究は、ベンチマーク上のエージェント軌跡の分析か、エンジニア間・組織間の比較に限られ、同じエンジニアのトークン消費と成果を時間を追って追った研究はなかった。本研究は、同一ツール環境で計測されたトークン数を使った人×週のパネルにより、個人の習慣的な利用量と週ごとの変動を分離した。さらにサーベイで、コミットにならない利用の中身まで確認した。

**技術や手法のキモはどこ？**

社内ゲートウェイの計測ログから週ごとのトークン消費を集計し、author dateで日付付けしたコミット数と結び付けて人×週パネルを作った。トークン数にはポアソン回帰（擬似最尤推定）を使い、個人・週の固定効果で個人内の弾力性を、Mundlak形式で個人間との差を推定した。成果に連動しない消費の割合は、成果ゼロの週の消費割合を下限（floor）、成果ゼロでの予測消費を外挿した曲線推定（スプラインなど）を上限として評価した。サーベイは、エージェントの用途や報告された削減時間を回帰分析し、自由記述を主題分析で整理した。

**どうやって有効だと検証した？**

個人内ではトークンを2倍にするとコミットは約10%増にとどまり、コミット数が近い週同士でも消費の90パーセンタイルは10パーセンタイルの39〜240倍だった。利用可能な作業指標は、消費の個人間変動の38%、個人内の週ごとの変動の13%しか説明せず、個人そのものが偏差の79%を説明した。成果に連動しない消費は下限で約4%、曲線推定では最大約39〜42%と見積もられた。サーベイでは、技術職のコーディングエージェント評価の89%でコーディング以外（分析・調査・計画など）の用途が報告された。

**議論はある？**

エンジニアが自分で消費量を選ぶため、結果は因果効果ではなく関連であり、1社・5週間・コミット数という限られた成果指標（品質やレビュー・設計は含まない）という制約がある。成果に連動しない消費の上限値には、エージェント利用の固定コストや手書きコードに伴う消費が含まれ、過大評価になりうる。サーベイは個人のログと結び付けられず、回答率も15.8%と低い。今後は、タスク内容や成果に基づく評価の手法が必要になる。

**次に読むべき論文は？**

- AI writes faster than humans can review: a longitudinal study of an enterprise 2x mandate：AIによる出力の増加とトークン消費の増加を企業で追跡した最も近いパネル研究で、本研究の結果と比較できる。
- Agentic coding in the wild: characterizing GitHub Copilot traces at production scale：本番環境でのエージェント利用ログの特性（利用量の個人差、探索・推論の比重）を理解する助けになる。
- How do AI agents spend your money? Analyzing and predicting token consumption in agentic coding tasks：タスクレベルでのトークン消費の内訳と、消費が成功率に結び付かない理由を押さえられる。

:::

### 2. コーディングエージェントは指示に従うか：コンテキストファイルの明示的指示への遵守を調査 {#paper-2}

arXiv ・ Gianmario Voria, Yutaro Kashiwa, Gemma Catolino, Fabio Palomba ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.13709)

<small>原題: Do They Do as They Are Told? Investigating Coding Agents' Adherence to Explicit Instructions in Context Files</small>

AGENTS.mdなどのエージェントコンテキストファイルに書いた指示が実際に守られるかを調べた研究です。従来の研究が内容の記述にとどまっていたのに対し、個々の指示の遵守を検証する点が特徴です。

::: tip 🔍 注目ポイント
コンテキストファイルによるガバナンスが前提とする「書けば守られる」という仮定を検証しています。
:::

::: info 📝 落合フォーマット

**どんなもの？**

AGENTS.md などのエージェントコンテキストファイル（ACF）に書かれた明示的・実行可能な指示が、コーディングエージェントが生成した実際のコミットに反映されているかを、指示単位で調べた実証研究。ACFの指示を抽出・分類し、実行可能な計測スクリプトに変換して遵守度を測定する。

**先行研究と比べてどこがすごい？**

従来のACF研究は内容を高位カテゴリで記述するにとどまり、個々の指示が守られているかは未検証だった。本研究は指示を「明示的・実行可能・観測可能」の3基準で絞り込み、指示ごとの計測スクリプトで、実リポジトリから採取したコミットに対する遵守度をカテゴリ別・エージェント別に分析した点が新しい。既存の遵守研究（RepoComplianceBenchなど）は統制された課題やAI貢献ポリシーが対象で、実際のコミットは扱っていない。

**技術や手法のキモはどこ？**

3段階のパイプラインを用いる。(1) 15件の手動キャリブレーションの後、Qwen 3.5 9Bによる少数例プロンプトでACFスナップショットから指示を抽出・分類し、84スナップショットを人手で検証した。(2) 各指示の「観測可能な振る舞い」記述から、Qwen2.5-Coder-14Bが計測スクリプト10本とテストフィクスチャ（準拠／非準拠のコミット対）10組を独立に生成する（CodeT型）。フィクスチャを2つ以上通過し、かつ別スクリプトと60%以上通過集合が重なるスクリプトのみ採用する。(3) 採用スクリプトを、AIDev由来の再構築コミット（6,541件、268リポジトリ）に適用して遵守を判定し、記述統計と比較検定で分析する。

**どうやって有効だと検証した？**

データは621のACFスナップショットと6,541件のエージェントコミットで、LLMは14,902件の指示を抽出した。人手検証の標本は84スナップショット（2,202指示）で、スクリプトの採用は4,123件、そのうち94件を抽出して人手で正しさを確認する設計とした。主な結果は、観測可能な指示の多くがスクリプト化でき、エージェントは平均して指示に「従う場合の方が多い」が、常に守られる指示とほぼ守られない指示に大きく二極化し、カテゴリとエージェントによって差があるというもの。本文の提供範囲では、遵守率や精度などの具体的な数値は確認できない。

**議論はある？**

遵守は成果物ベースの代理指標で測っており、エージェントの意図や内部推論は見ていない。人手検証は単一アノテータで、スクリプトの採用基準（2フィクスチャ・60%重なり）もパイロットで決めており、誤ったスクリプトを採用するリスクがある。観測不能な指示は分析対象外で、LLMの非決定性も限界となる。今後は、守られにくい指示の書き換えや、ACFの外側で検証・強制する仕組みの設計が課題となる。

**次に読むべき論文は？**

### 3. Spec-Driven PBT：コード仕様から意味的不変条件を導くエージェント型プロパティベーステスト {#paper-3}

arXiv ・ Aditya Shukla, Kartik Gupta, Ali Alavi, Pashootan Vaezipoor ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.15920)

<small>原題: Spec-Driven PBT: Deriving Semantic Invariants from Code Specifications for Agentic Property-based Testing</small>

エージェントによるコーディングで、コード生成がレビューより速くなっている問題に対し、仕様から不変条件を導出してプロパティベーステストに使う手法を提案しています。LLMエージェントにプロパティを書かせる流れを踏まえた研究です。

::: tip 🔍 注目ポイント
AI生成コードの検証手段として、前述のテスト議論と関連する具体的な手法です。
:::

::: info 📝 落合フォーマット

**どんなもの？**

エージェントが自然言語の仕様書（PRD）からセマンティックな不変条件を導出し、それを基にPython Hypothesisのプロパティベーステスト（PBT）を書いてAI生成コードのバグを探す手法「Spec-Driven PBT」を提案した研究。実装だけから性質を導く従来のCode-driven PBTと比較し、仕様を情報源とする価値を検証している。

**先行研究と比べてどこがすごい？**

既存のエージェント型PBT（Agentic PBT）は実装・docstring・コメントから性質を導くため、実装が一貫して誤っている挙動を検出できない。本手法は「まず実装を見ずに仕様から不変条件を自然言語で記録し、その後でコードを反証入力探索にのみ使う（オラクルにしない）」という情報境界を設け、不変条件を監査可能な台帳（invariants.md）として残す点が新しい。

**技術や手法のキモはどこ？**

エージェントは(1)仕様のみから初期不変条件をinvariants.mdに記録、(2)コードを調べて不変条件を精緻化しつつ反証しうる入力・境界・操作列を探す、(3)影響の大きい少数を優先、(4)Hypothesisテストへ変換、(5)pytestで実行し失敗を正当性確認、(6)再現手順・修正案付きのバグ報告を作成する。Claude Opus 5をClaude Codeで動かし、プロンプトのみで構築する軽量な設計で、ベースラインはMaaz et al.のAgentic PBTを適応したもの。

**どうやって有効だと検証した？**

ViBenchの25アプリで、ブラインドLLMレビュアーが両手法の失敗テストを統合・重複排除したところ、全169件のバグのうち70件が両方、56件が提案手法のみ、43件がベースラインのみで検出され（Jaccard 41%）、テスト数は566対1,384（約2.4倍少ない）、バグに結びつくテスト割合は34%対13%だった。PBTBench（注入バグ365件）では再現率88%対85%、重複は大きく（Jaccard 84%）、仕様がAPIリファレンス型でコード寄りなためと推測されている。質的分析では、提案手法固有のバグは状態・ライフサイクルや論理・計算（61%）、Code-driven固有は入力処理（49%）が中心だった。

**議論はある？**

ViBenchには正解バグラベルがなくLLMレビュアーに依存し、手動検証も25件の部分集合に限られる。また両手法はプロンプトやワークフローも異なるため、効率差が仕様根拠のみによるとは断定できず、仕様が薄い・古い場合は性能低下が予想される。PBTは網羅的でなく、人間によるレビューを完全に代替しない。

**次に読むべき論文は？**

- Agentic Property-Based Testing: Finding Bugs Across the Python Ecosystem：本論文のベースラインであるCode-driven PBTの元手法で、write–run–triageループの基礎を理解できる。
- Specification grounding drives test effectiveness for LLM code：仕様に基づくテスト作成が有効であり、コードを読むテスト作成者がバグを意図された挙動とみなす偏りを示した、本研究の動機に直結する先行研究。
- ViBench: A benchmark on vibe coding：本論文の主要評価基盤であるPRDからのアプリ生成ベンチマークの詳細と失敗分析を把握できる。

:::

### 4. ADAPT：プルリクエスト向けのエージェント型差分対応パッチテスト {#paper-4}

arXiv ・ Vahid Haratian, Atakan Akar, Eray Tüzün ・ [論文を読む ↗](https://arxiv.org/abs/2611.16114)

<small>原題: ADAPT: Agentic Diff-Aware Patch Testing for Pull Requests</small>

PRで導入された変更の振る舞いを守るテストが欠けがちな点に着目し、差分を意識してテストを生成するエージェント手法を提案しています。コードカバレッジではなく、PRが導入する振る舞いを対象にします。

::: tip 🔍 注目ポイント
コードレビューのプロセスにテスト生成を組み込む実務的な方向性です。
:::

::: info 📝 落合フォーマット

**どんなもの？**

プルリクエスト（PR）の差分だけから、その変更が導入した振る舞いを検証する回帰テストを自動生成するエージェント型手法 ADAPT を提案した研究。PRにテストが付かないまま取り込まれ、新しい振る舞いが将来の退行から守られない問題に対処する。

**先行研究と比べてどこがすごい？**

従来のテスト生成はクラスやモジュール全体を対象にカバレッジを最適化するものが多く、差分を考慮した先行手法（BLAST など）も成功率が限られていた。ADAPT はPR単位のテスト生成にエージェント型ワークフローを初めて適用し、issue 記述なしにコード変更のみから生成する点が新しい。base/head 両バージョンでの Fail-to-Pass（F2P）検証をツール化し、生成中の能動的なフィードバックとして使う点も特徴である。

**技術や手法のキモはどこ？**

OpenHands 上に構築した自律エージェントが、diff から変更関数と文脈を把握し、既存テストの規約を学んでテストを計画・生成する。独自の F2P 検証ツールが、別ワークスペースで head と base の両方に候補テストを実行し、「head で通らない」「base でも通ってしまう（汎用的すぎる）」といった失敗原因を診断として返す。F2P 成功後は、実行可能な変更行のうち未カバーの行をソースとともに報告し、パッチカバレッジ100%を目指して反復的にテストを改良させる。リーク防止のため .git とテストパッチは生成環境から除外し、既存ファイルの編集も禁止している。

**どうやって有効だと検証した？**

SWE-bench Verified の426件のPR（BLAST と同一のデータセット）で評価した。同じ GPT-4o での F2P 率は ADAPT 62.0%（264/426）、BLAST 35.4%（151/426）で、+26.6ポイントとなった。GPT-5-mini では 89.9%（383/426）で、総コストは GPT-4o の約29分の1（$16.62 対 $478.95）だった。ChaCo との共通137件のPRでは完全パッチカバレッジが 83.9% 対 79.6% で、時間・コストも低いと報告されている。人手評価（70件、4名）では F2P 有効テストの平均が重要度 4.54、アサーション強度 4.35、可読性 4.49（GPT-5-mini、5点満点）で、開発者作成テストより広い振る舞いを含む割合は64〜66%だった。

**議論はある？**

エラーは GPT-4o では主にステップ上限超過、GPT-5-mini ではすべてタイムアウトであり、効率面に課題が残る。開発者作成テストが生成テストにない振る舞いをカバーしている割合も78〜81%と高く、生成テストは開発者テストを完全には代替しない。評価は主に Python リポジトリが対象で、F2P 判定にはPR後の head 実装が前提となるため、他言語や実運用への一般化、および比較条件の差（ステップ・時間上限など）には議論の余地がある。

**次に読むべき論文は？**

- Automated generation of issue-reproducing tests by combining LLMs and search-based testing (BLAST)：本研究の主要ベースラインであり、F2P テスト生成の先行手法と評価設定を理解できる。
- Change and Cover: Last-mile, pull request-based regression test augmentation (ChaCo)：PRの変更行カバレッジを目的とする関連手法で、RQ4 の比較対象として手法の違いを把握できる。
- OpenHands: An open platform for AI software developers as generalist agents：ADAPT の基盤となるエージェントのアクション・観測ループの仕組みを理解できる。

:::

### 5. AgentTorrent：GitHub上のコンテキスト・ハーネスエンジニアリング成果物のデータセット {#paper-5}

arXiv ・ Sebastian Baltes, Seyedmoein Mohsenimofidi, Levi Böhme, Vahram Nersesyan ほか ・ [論文を読む ↗](https://arxiv.org/abs/2611.15436)

<small>原題: AgentTorrent: A Dataset of Context and Harness Engineering Artifacts on GitHub</small>

コンテキストファイル、スキル、フック、MCP設定、仕様やプラン、タスクファイルなど、エージェント型コーディングツールの設定成果物をGitHubから集めたデータセットです。開発者がプロンプトからコンテキストとハーネスの設計へ移行している状況を背景にしています。

::: tip 🔍 注目ポイント
コンテキストエンジニアリングの実態を研究・分析するための基礎資料になります。
:::

::: info 📝 落合フォーマット

**どんなもの？**

GitHub上の10,944件の「エンジニアリングされたソフトウェアプロジェクト」から、エージェント型コーディングツール6種（Claude Code、Copilot、Codex、Cursor、Gemini、OpenCode）の設定アーティファクト（コンテキストファイル、スキル、フック、MCP設定など）、それがimportするファイル、計画文書（仕様・計画・タスク）、AIツールをクレジットしたコミットを収集したデータセットAgentTorrentを提案している。62,374件の設定アーティファクト、27,593件の計画文書、120万件超のクレジット付きコミットを含み、パイプラインとともにZenodoで公開されている。

**先行研究と比べてどこがすごい？**

既存データセットは個別のアーティファクト種別に限られ、リポジトリのサンプルや収集時期も異なるため統合が難しかった。本データセットは設定アーティファクト、import、計画文書、クレジット付きコミットを同一リポジトリ内で結びつけた唯一のデータセットである。また、各検出ヒューリスティクスがベンダー文書やGitHub上の事例に根拠を持ち、精度だけでなく再現率も評価している点、設定の有無と独立にサンプリングして普及率の分母を提供する点が優れている。前身のAgentConfigs（15,591件・5ツール）から約4倍に拡大した。

**技術や手法のキモはどこ？**

SEART GitHub Searchで条件に合う46,503リポジトリを抽出し、オープンウェイトモデル（DeepSeek V4.1 Flash）がREADMEやメタデータなどから、教材やテンプレートを除外しつつ2つ以上のエンジニアリング実践があるかを判定して、40,901件のエンジニアリングされたプロジェクトを得る。次に、ベンダー文書に根拠を持つ358のパスヒューリスティクスで設定ファイルを収集し、各ツールの読み込み規則（Claude Codeのimport深さ上限4など）に従ってimportを解決し、73のフレームワークに対応する523のヒューリスティクスで計画文書を検出する。コミットの帰属は著者・コミッタ識別子とメッセージ（共著トレーラー等）から、431のヒューリスティクスで判定する。週次でベンダー文書438ページを監視し、未知のパスやクレジットを検出する自動チェックを備え、四半期ごとの更新を想定している。

**どうやって有効だと検証した？**

リポジトリ分類では、第2のモデル（GLM-5.3）との一致率が1,039件中1,018件（98.0%、κ=0.87）だった。検出精度は、設定アーティファクト99.87%、6ツールのクレジットコミット99.96%、import 99.98%、計画文書99.8%と推定された（信頼区間の下限はいずれも比較的広く、90.5〜96.6%）。再現率は、検出のある100リポジトリで386件中383件を検出し、検出のない200リポジトリで見逃しは1件、コミットの一様サンプル1,000件ではクレジット付き19件中18件を検出した。また、リポジトリ由来のヒューリスティクスが、文書ベースでは見逃す312,453件のクレジットコミットを検出した。

**議論はある？**

設定アーティファクトの存在はツールの実際の使用を示さず、クレジットも貢献度や無クレジットの利用を測れない。調査対象はデフォルトブランチ、アクティブでライセンスのある10言語のプロジェクトに限られ、検出ラベルもClaude Code由来のヒューリスティクスと同一モデルで評価しているため独立ではない。今後は各パスヒューリスティクスの精度評価や、ファイルが現在のパスに最初に現れた日付の特定を計画している。

- Agentic much? Adoption of coding agents on GitHub：GitHub上でのコーディングエージェントの普及を設定ファイルなどから測定した代表的先行研究で、本データセットの動機と比較対象を理解できる。
- A dataset of agentic AI coding tool configurations：AgentTorrentの前身であるAgentConfigsデータセットで、収集方法の出発点と拡張点を把握できる。
- Spec-driven development as prescribed and as practiced：本データセットが収集する計画文書（仕様・計画・タスク）に関連するSpecMineデータセットの研究で、仕様駆動開発の実態を理解できる。
